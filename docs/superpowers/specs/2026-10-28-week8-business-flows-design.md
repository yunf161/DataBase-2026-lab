# 第八周业务流程与集成验证设计

## 目标与边界

基于 `lzq` 分支现有的 Flask、SQL Server v1.0/W7 应用，完成课程第八周“面向角色的操作界面、事务边界和集成测试”。本周展示从 Web 界面提交采购入库、销售结算与受控盘点，验证订单、明细、库存及流水的一致性。顾客继续只能操作自己的销售草稿。第九周最终报告与跨周总验收另行完成，不把草稿当作已完成交易，也不实施退货或会员业务。

## 两种实现路径与选择

方案 A：在现有 `dbo.ConfirmPurchase`、`dbo.CompleteSale` 外增加应用层受限入口，复用它们的锁、金额计算、库存更新与流水事务；盘点新增一个单独受控过程。Python 的 service 做输入和角色检查，repository 只调用参数化 SQL。方案 B：在 Python 中重新计算并逐表写入订单、库存和流水。方案 B 会复制现有数据库业务规则，增加两套逻辑偏离和部分提交风险。采用方案 A。

## 功能与权限

管理员可查询采购单、创建采购草稿、增改删采购明细、确认入库；可查询库存并以非零差额执行盘点，必须填写原因。管理员和店员可对可见的销售草稿执行结算；顾客只可查看自己的订单与草稿，不能确认采购、结算或盘点。所有角色都不能直接通过 Web 参数指定完成状态、总额、库存变动前后值或库存流水。

新建 `sql/week8/application.sql`，仅部署到已经完成第六周迁移、且部署了第七周应用增量的 `CampusStoreDB_W7_*` 独立库。该脚本增加受限采购视图/过程、销售结算包装过程、盘点过程和最小授权，不改变第一至第七周的提交包或正式 `CampusStoreDB`。准备工具在新测试/开发副本中按 W7→W8 顺序部署；已有 W7 开发库需提供安全的增量部署说明，不静默覆盖数据。

采购确认调用核心 `dbo.ConfirmPurchase`，销售结算调用核心 `dbo.CompleteSale`。这两者已有事务、锁和状态保护。盘点过程在同一事务锁定库存、验证变化量和非负结果、更新 `Inventory.Quantity` 并写 `InventoryLog` 的 `STOCKTAKE_IN`/`STOCKTAKE_OUT`；不伪造采购/销售来源 ID。库存不足、非法数量、重复确认或权限不足时，不留下部分订单/库存/流水。数据库授权与后端角色检查一致，前端按钮只是可见性提示。

## 页面与接口

沿用 `app/routes.py` → `app/services.py` → `app/repositories.py` → SQL Server 的层次。新增采购单查询/草稿/明细/确认 API、销售结算 API、盘点 API，复用现有 JSON 响应、CSRF、参数校验和异常日志。页面沿用现有布局，管理员增加采购及盘点操作，管理员/店员的草稿详情增加结算操作；顾客界面不出现这些入口。操作后重新查询真实订单状态、库存和流水，界面不能仅凭本地计算宣布成功。

## 验证与交付

先写失败用例，再逐点实现。真实 SQL Server 隔离库的集成测试覆盖多商品采购入库、销售结算和库存扣减、盘点增减、事务回滚、重复提交、库存不足、权限拒绝、CSRF、约束冲突与统一友好错误。浏览器测试覆盖管理员/店员/顾客界面和核心流程。每次验证建立随机测试库并清理，正式 `CampusStoreDB` 保持 v0.1。更新 README、API/架构/操作手册，新增第八周结果记录与报告素材；通过验证后只暂存本次交付文件并推送 `lzq`。
