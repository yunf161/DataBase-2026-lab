# 第二阶段第5—6周报告素材

本素材用于整理第二阶段报告中的设计思路、实验过程和实验总结。
本版覆盖 ER 建模、函数依赖与范式取舍、迁移和回归，不表示第7—9周应用开发完成。
组员姓名和具体贡献按实际工作另行填写，AI记录本次不调整。

## 设计思路

校园小卖部围绕商品、分类、供应商、员工、采购、销售和库存管理业务。
管理员、采购员、收银员职责区分；采购和销售采用订单头/明细结构，先建草稿再确认或结算。
商品当前售价与历史成交价分开保存，库存快照和变化流水分开保存。
主要业务实体共10个，两张订单明细表表达订单与商品的多对多联系。

第五周从实际主键、非空唯一键、可空唯一索引和外键识别标识及联系。
将草稿可无明细与完成订单至少一条明细区分，将商品→库存业务1..1与实际PK+FK的0..1区分。
图中央a/b标签统一按业务规则表左→右读取。会员仅作为第五周讨论方案，
第六周确认不保存顾客身份，取消拟议会员；同商品一单一行的规则保留。
见[第五周设计说明](../week5-er/README.md)和[业务规则](../week5-er/business-rules.md)。

## 函数依赖和规范化取舍

候选码必须决定全体属性，包括其他候选码。Barcode可空，不能作为全表候选码；
外键参照关系不能直接冒充本行函数依赖，当前商品价格也不决定历史成交价。
基础业务属性关系在已确认依赖下达到3NF；完整物理关系的LineAmount、PayableAmount
以及BeforeQuantity、ChangeQuantity决定AfterQuantity，存在非码派生依赖，严格判断不全部满足3NF。

计算列免于人工同步，库存前后值由CHECK校验；订单头总额和当前库存由锁定的事务过程维护，
普通角色无直接库存数量写入权限。这些物理冗余有审计和查询收益，因此保留并说明维护责任。
对独立销售宽表示例逐次提取员工、分类、商品和订单头，用交集决定子关系证明无损，
用依赖落在子关系内证明保持；该教学分解不额外建业务表。
逐表三类异常、依据和方案见[范式分析](normalization-analysis.md)。

## 迁移实验过程

1. 保存冻结第一阶段提交，完整v0.1数据库副本是迁移初始状态；
   自动验证以冻结脚本替换库名建立随机副本，正式库不作为测试目标。
2. baseline保存订单头/明细、商品销售、库存、完整流水和12项指标。
3. migration检查每条旧BusinessNo与正确类型订单唯一匹配，将来源改为PurchaseID/SaleID，
   增加FK、来源互斥与数量方向CHECK和索引，再升级过程、状态保护、视图和权限。
4. 用LEFT JOIN与COALESCE重构BusinessNo，保留盘点空来源，不复制或丢弃流水。
5. migration事务中任一步失败整体回滚；成功后拒绝重复运行。
   数据冲突需核实业务凭据，不猜测来源。手动展示从还原副本执行，不重跑固定库名01/03。

来源改造是表示替换，单号与订单ID的一一对应及类型约束使重构可逆；
终态编号保护是历史显示等价的前提。样例回归是实施证据，不能代替设计层面证明。
见[目标结构](target-schema.md)与[恢复说明](migration-notes.md)。

## 实验总结与当前边界

规范化分析需要考虑所有候选码与派生字段，增加自增主码和计算列并不自动消除非码依赖。
项目选择保留有维护机制的冗余，集中修复旧文本来源的参照完整性，并通过故障注入检验事务边界。
订单状态保护还需要显式处理SQL三值逻辑，缺失过程标记不能绕过业务流程；
权限控制和触发器相互配合，SESSION_CONTEXT不是对管理员的独立安全凭据。

冻结提交、原截图和AI记录保持原样，正式库校验快照前后一致，随机测试库已清理。
本版第5—6周技术材料、脚本和验证已整理；AI过程记录按组内安排另行核对，
第7—9周应用开发与最终第二阶段报告后续完成。退货/盘点只预留类型，未实现过程。
