下面以 **MySQL 8.0.16+** 为例，设计一个课程项目级的"小卖部进销存数据库"。核心包含 10 张表，既能展示规范化设计，又不会复杂到难以实现。

## 1\. 整体表关系

```
商品分类 category
    1 ───── N 商品 product
                  │
                  │ 1
                  │
                  1 库存 inventory
                  │
                  └──── N 库存流水 inventory_log
供应商 supplier
    1 ───── N 采购单 purchase_order
                    1
                    │
                    N
                采购明细 purchase_item
                    N
                    │
                    1
                  商品 product
员工 employee
    1 ───── N 采购单 purchase_order
    1 ───── N 销售单 sale_order
销售单 sale_order
    1 ───── N 销售明细 sale_item
                    N
                    │
                    1
                  商品 product
```

核心设计原则：

- 商品当前库存放在 inventory。
- 每次库存变化记录在 inventory_log。
- 采购单和销售单都采用"订单头＋订单明细"结构。
- 商品表只保存当前销售价格。
- 销售明细必须保存成交时的单价，避免商品改价后历史订单发生变化。
- 已完成的订单不直接删除，通过状态控制。
- 只有"确认入库"和"完成销售"时才修改库存。

# 2\. 各表详细设计

## 2.1 商品分类表 category

用于管理饮料、零食、文具、日用品等分类。

| **字段**      | **类型**     | **说明**       |
| ------------- | ------------ | -------------- |
| category_id   | BIGINT       | 分类主键       |
| category_code | VARCHAR(20)  | 分类编号，唯一 |
| category_name | VARCHAR(50)  | 分类名称       |
| parent_id     | BIGINT       | 父分类，可为空 |
| description   | VARCHAR(255) | 分类说明       |
| status        | TINYINT      | 1启用，0停用   |
| created_at    | DATETIME     | 创建时间       |
| updated_at    | DATETIME     | 修改时间       |

parent_id 可以实现二级分类，例如：

```
食品
├── 饮料
├── 面包
└── 方便食品
```

如果你们不需要多级分类，也可以保留该字段但不使用。

## 2.2 商品表 product

保存商品的基本资料，不直接保存当前库存。

| **字段**      | **类型**      | **说明**           |
| ------------- | ------------- | ------------------ |
| product_id    | BIGINT        | 商品主键           |
| sku           | VARCHAR(30)   | 内部商品编号       |
| barcode       | VARCHAR(32)   | 商品条码           |
| product_name  | VARCHAR(100)  | 商品名称           |
| category_id   | BIGINT        | 所属分类           |
| specification | VARCHAR(100)  | 规格，如500ml      |
| unit          | VARCHAR(20)   | 单位，如瓶、袋、盒 |
| sale_price    | DECIMAL(10,2) | 当前销售价格       |
| status        | TINYINT       | 1在售，0停用       |
| created_at    | DATETIME      | 创建时间           |
| updated_at    | DATETIME      | 修改时间           |

注意：

- sku 和 barcode 都应唯一。
- 条码要用字符串，不要用数字，否则可能丢失前导零。
- 不建议在商品表里固定采购价，因为每次采购价格可能不同。
- 不建议物理删除已经产生销售记录的商品，应将 status 改成 0。

## 2.3 供应商表 supplier

| **字段**      | **类型**     | **说明**     |
| ------------- | ------------ | ------------ |
| supplier_id   | BIGINT       | 供应商主键   |
| supplier_code | VARCHAR(20)  | 供应商编号   |
| supplier_name | VARCHAR(100) | 供应商名称   |
| contact_name  | VARCHAR(50)  | 联系人       |
| phone         | VARCHAR(30)  | 联系电话     |
| address       | VARCHAR(255) | 地址         |
| status        | TINYINT      | 1正常，0停用 |
| created_at    | DATETIME     | 创建时间     |
| updated_at    | DATETIME     | 修改时间     |

供应商停用后，历史采购记录仍然需要保留，所以不能直接删除。

## 2.4 员工表 employee

即使不做前端和登录，也建议保留员工表，用于记录是谁完成采购、入库或销售。

| **字段**      | **类型**    | **说明**     |
| ------------- | ----------- | ------------ |
| employee_id   | BIGINT      | 员工主键     |
| employee_no   | VARCHAR(20) | 员工编号     |
| employee_name | VARCHAR(50) | 姓名         |
| role          | VARCHAR(20) | 角色         |
| phone         | VARCHAR(30) | 电话         |
| status        | TINYINT     | 1在职，0停用 |
| created_at    | DATETIME    | 创建时间     |

角色可以设置为：

- ADMIN：管理员
- PURCHASER：采购员
- CASHIER：收银员

课程项目不做权限系统时，不需要保存密码。

## 2.5 库存表 inventory

每种商品对应一条库存记录。

| **字段**     | **类型** | **说明**             |
| ------------ | -------- | -------------------- |
| product_id   | BIGINT   | 商品主键，同时是外键 |
| quantity     | INT      | 当前库存数量         |
| min_quantity | INT      | 最低库存数量         |
| updated_at   | DATETIME | 最近更新时间         |

这里使用 product_id 作为主键，表示商品与库存是一对一关系。

例如：

| **商品** | **当前库存** | **最低库存** |
| -------- | ------------ | ------------ |
| 可乐     | 80           | 20           |
| 面包     | 6            | 10           |
| 纸巾     | 30           | 10           |

面包库存低于最低库存，因此应该出现在低库存预警中。

## 2.6 采购单表 purchase_order

采购单的总体信息，相当于"订单头"。

| **字段**      | **类型**      | **说明**   |
| ------------- | ------------- | ---------- |
| purchase_id   | BIGINT        | 采购单主键 |
| purchase_no   | VARCHAR(30)   | 采购单号   |
| supplier_id   | BIGINT        | 供应商     |
| employee_id   | BIGINT        | 经办员工   |
| order_time    | DATETIME      | 下单时间   |
| received_time | DATETIME      | 入库时间   |
| status        | VARCHAR(20)   | 采购单状态 |
| total_amount  | DECIMAL(12,2) | 采购总金额 |
| remark        | VARCHAR(255)  | 备注       |
| created_at    | DATETIME      | 创建时间   |
| updated_at    | DATETIME      | 修改时间   |

推荐状态：

| **状态**  | **含义** | **是否影响库存** |
| --------- | -------- | ---------------- |
| DRAFT     | 草稿     | 否               |
| RECEIVED  | 已入库   | 是               |
| CANCELLED | 已取消   | 否               |

从 DRAFT 变成 RECEIVED 时：

1. 检查采购明细；
2. 增加商品库存；
3. 写入库存流水；
4. 计算采购总金额；
5. 记录入库时间。

## 2.7 采购明细表 purchase_item

保存采购单中每一种商品的信息。

| **字段**         | **类型**      | **说明**     |
| ---------------- | ------------- | ------------ |
| purchase_item_id | BIGINT        | 明细主键     |
| purchase_id      | BIGINT        | 所属采购单   |
| product_id       | BIGINT        | 商品         |
| quantity         | INT           | 采购数量     |
| unit_cost        | DECIMAL(10,2) | 本次采购单价 |
| line_amount      | DECIMAL(12,2) | 行金额       |

计算公式：

```
行金额 = 采购数量 × 采购单价
采购总金额 = 所有采购明细行金额之和
```

同一个商品的采购价可能随时间变化，因此采购价必须保存在采购明细表中。

## 2.8 销售单表 sale_order

保存每笔销售的总体信息。

| **字段**        | **类型**      | **说明**     |
| --------------- | ------------- | ------------ |
| sale_id         | BIGINT        | 销售单主键   |
| sale_no         | VARCHAR(30)   | 销售单号     |
| employee_id     | BIGINT        | 收银员工     |
| sale_time       | DATETIME      | 销售时间     |
| status          | VARCHAR(20)   | 销售状态     |
| total_amount    | DECIMAL(12,2) | 商品原始总额 |
| discount_amount | DECIMAL(12,2) | 优惠金额     |
| payable_amount  | DECIMAL(12,2) | 实付金额     |
| payment_method  | VARCHAR(20)   | 支付方式     |
| remark          | VARCHAR(255)  | 备注         |
| created_at      | DATETIME      | 创建时间     |

推荐状态：

| **状态**  | **含义** | **是否影响库存** |
| --------- | -------- | ---------------- |
| DRAFT     | 草稿     | 否               |
| COMPLETED | 已完成   | 是               |
| CANCELLED | 已取消   | 否               |
| REFUNDED  | 已退货   | 需要恢复库存     |

支付方式可以是：

- CASH
- WECHAT
- ALIPAY
- BANK_CARD

实付金额计算公式：

```
实付金额 = 商品总额 - 优惠金额
```

## 2.9 销售明细表 sale_item

| **字段**     | **类型**      | **说明**   |
| ------------ | ------------- | ---------- |
| sale_item_id | BIGINT        | 明细主键   |
| sale_id      | BIGINT        | 所属销售单 |
| product_id   | BIGINT        | 商品       |
| quantity     | INT           | 销售数量   |
| unit_price   | DECIMAL(10,2) | 成交时单价 |
| line_amount  | DECIMAL(12,2) | 行金额     |

unit_price 必须保留成交时的价格。

例如，可乐现在售价是 3 元，一个月后涨价到 3.5 元。历史订单仍应显示当时成交的 3 元，而不是读取商品表中的最新价格。

## 2.10 库存流水表 inventory_log

记录库存为什么发生变化，是系统可追溯性的关键。

| **字段**        | **类型**     | **说明**     |
| --------------- | ------------ | ------------ |
| log_id          | BIGINT       | 流水主键     |
| product_id      | BIGINT       | 商品         |
| change_type     | VARCHAR(20)  | 变化类型     |
| change_quantity | INT          | 变化数量     |
| before_quantity | INT          | 变化前库存   |
| after_quantity  | INT          | 变化后库存   |
| business_no     | VARCHAR(30)  | 关联业务单号 |
| employee_id     | BIGINT       | 操作员工     |
| remark          | VARCHAR(255) | 说明         |
| created_at      | DATETIME     | 发生时间     |

change_quantity 使用带符号整数：

- 采购入库 50 件：+50
- 销售 3 件：-3
- 销售退货 2 件：+2
- 盘点发现少 1 件：-1

推荐变化类型：

- PURCHASE_IN
- SALE_OUT
- SALE_RETURN
- PURCHASE_RETURN
- STOCKTAKE_IN
- STOCKTAKE_OUT

# 3\. 完整建表 SQL

```
CREATE DATABASE IF NOT EXISTS convenience_store
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_0900_ai_ci;
USE convenience_store;
```

## 3.1 商品分类表

```
CREATE TABLE category (
    category_id BIGINT UNSIGNED AUTO_INCREMENT,
    category_code VARCHAR(20) NOT NULL,
    category_name VARCHAR(50) NOT NULL,
    parent_id BIGINT UNSIGNED NULL,
    description VARCHAR(255) NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (category_id),
    UNIQUE KEY uk_category_code (category_code),
    KEY idx_category_parent (parent_id),
    CONSTRAINT fk_category_parent
        FOREIGN KEY (parent_id)
        REFERENCES category(category_id)
        ON UPDATE CASCADE
        ON DELETE SET NULL,
    CONSTRAINT chk_category_status
        CHECK (status IN (0, 1))
) ENGINE = InnoDB;
```

## 3.2 商品表

```
CREATE TABLE product (
    product_id BIGINT UNSIGNED AUTO_INCREMENT,
    sku VARCHAR(30) NOT NULL,
    barcode VARCHAR(32) NULL,
    product_name VARCHAR(100) NOT NULL,
    category_id BIGINT UNSIGNED NOT NULL,
    specification VARCHAR(100) NULL,
    unit VARCHAR(20) NOT NULL DEFAULT '件',
    sale_price DECIMAL(10, 2) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (product_id),
    UNIQUE KEY uk_product_sku (sku),
    UNIQUE KEY uk_product_barcode (barcode),
    KEY idx_product_name (product_name),
    KEY idx_product_category (category_id),
    CONSTRAINT fk_product_category
        FOREIGN KEY (category_id)
        REFERENCES category(category_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT chk_product_price
        CHECK (sale_price >= 0),
    CONSTRAINT chk_product_status
        CHECK (status IN (0, 1))
) ENGINE = InnoDB;
```

## 3.7 采购明细表

```
CREATE TABLE purchase_item (
    purchase_item_id BIGINT UNSIGNED AUTO_INCREMENT,
    purchase_id BIGINT UNSIGNED NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,
    quantity INT NOT NULL,
    unit_cost DECIMAL(10, 2) NOT NULL,
    line_amount DECIMAL(12, 2)
        GENERATED ALWAYS AS (quantity * unit_cost) STORED,
    PRIMARY KEY (purchase_item_id),
    UNIQUE KEY uk_purchase_product (purchase_id, product_id),
    KEY idx_purchase_item_product (product_id),
    CONSTRAINT fk_purchase_item_order
        FOREIGN KEY (purchase_id)
        REFERENCES purchase_order(purchase_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT fk_purchase_item_product
        FOREIGN KEY (product_id)
        REFERENCES product(product_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT chk_purchase_item_quantity
        CHECK (quantity > 0),
    CONSTRAINT chk_purchase_item_cost
        CHECK (unit_cost >= 0)
) ENGINE = InnoDB;
```

line_amount 是生成列，不需要手动插入。

例如：

```
INSERT INTO purchase_item
    (purchase_id, product_id, quantity, unit_cost)
VALUES
    (1, 1, 100, 2.20);
```

数据库自动计算：

```
line_amount = 100 × 2.20 = 220.00
```

## 3.8 销售单表

```
CREATE TABLE sale_order (
    sale_id BIGINT UNSIGNED AUTO_INCREMENT,
    sale_no VARCHAR(30) NOT NULL,
    employee_id BIGINT UNSIGNED NOT NULL,
    sale_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',
    total_amount DECIMAL(12, 2) NOT NULL DEFAULT 0,
    discount_amount DECIMAL(12, 2) NOT NULL DEFAULT 0,
    payable_amount DECIMAL(12, 2)
        GENERATED ALWAYS AS (total_amount - discount_amount) STORED,
    payment_method VARCHAR(20) NULL,
    remark VARCHAR(255) NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (sale_id),
    UNIQUE KEY uk_sale_no (sale_no),
    KEY idx_sale_employee (employee_id),
    KEY idx_sale_time (sale_time),
    KEY idx_sale_status (status),
    CONSTRAINT fk_sale_employee
        FOREIGN KEY (employee_id)
        REFERENCES employee(employee_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT chk_sale_status
        CHECK (
            status IN (
                'DRAFT',
                'COMPLETED',
                'CANCELLED',
                'REFUNDED'
            )
        ),
    CONSTRAINT chk_sale_payment
        CHECK (
            payment_method IS NULL
            OR payment_method IN (
                'CASH',
                'WECHAT',
                'ALIPAY',
                'BANK_CARD'
            )
        ),
    CONSTRAINT chk_sale_amount
        CHECK (
            total_amount >= 0
            AND discount_amount >= 0
            AND discount_amount <= total_amount
        )
) ENGINE = InnoDB;
```

## 3.10 库存流水表

```
CREATE TABLE inventory_log (
    log_id BIGINT UNSIGNED AUTO_INCREMENT,
    product_id BIGINT UNSIGNED NOT NULL,
    change_type VARCHAR(30) NOT NULL,
    change_quantity INT NOT NULL,
    before_quantity INT NOT NULL,
    after_quantity INT NOT NULL,
    business_no VARCHAR(30) NULL,
    employee_id BIGINT UNSIGNED NULL,
    remark VARCHAR(255) NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (log_id),
    KEY idx_inventory_log_product_time (product_id, created_at),
    KEY idx_inventory_log_business_no (business_no),
    KEY idx_inventory_log_employee (employee_id),
    CONSTRAINT fk_inventory_log_product
        FOREIGN KEY (product_id)
        REFERENCES product(product_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT fk_inventory_log_employee
        FOREIGN KEY (employee_id)
        REFERENCES employee(employee_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT chk_inventory_log_type
        CHECK (
            change_type IN (
                'PURCHASE_IN',
                'SALE_OUT',
                'SALE_RETURN',
                'PURCHASE_RETURN',
                'STOCKTAKE_IN',
                'STOCKTAKE_OUT'
            )
        ),
    CONSTRAINT chk_inventory_log_quantity
        CHECK (
            change_quantity <> 0
            AND before_quantity >= 0
            AND after_quantity >= 0
            AND after_quantity =
                before_quantity + change_quantity
        )
) ENGINE = InnoDB;
```

# 4\. 为什么库存流水不直接外键关联订单

库存流水可能来自多种业务：

- 采购单
- 销售单
- 销售退货
- 采购退货
- 库存盘点

如果只设计一个 business_id，它无法同时外键关联多张订单表。因此课程项目中可以保存：

```
change_type = 'SALE_OUT'
business_no = 'SO202609160001'
```

然后根据 change_type 判断业务类型。

这是有意设计，不是忘记添加外键。

# 6\. 建议补充的视图

## 6.1 当前库存视图

```
CREATE VIEW v_current_inventory AS
SELECT
    p.product_id,
    p.sku,
    p.barcode,
    p.product_name,
    c.category_name,
    p.specification,
    p.unit,
    p.sale_price,
    i.quantity,
    i.min_quantity,
    CASE
        WHEN i.quantity = 0 THEN 'OUT_OF_STOCK'
        WHEN i.quantity < i.min_quantity THEN 'LOW_STOCK'
        ELSE 'NORMAL'
    END AS stock_status,
    i.updated_at
FROM product AS p
JOIN category AS c
    ON c.category_id = p.category_id
JOIN inventory AS i
    ON i.product_id = p.product_id;
```

查询低库存商品：

```
SELECT *
FROM v_current_inventory
WHERE stock_status IN ('LOW_STOCK', 'OUT_OF_STOCK');
```

## 6.2 销售明细视图

```
CREATE VIEW v_sale_detail AS
SELECT
    so.sale_no,
    so.sale_time,
    e.employee_name,
    p.sku,
    p.product_name,
    si.quantity,
    si.unit_price,
    si.line_amount,
    so.payment_method
FROM sale_order AS so
JOIN employee AS e
    ON e.employee_id = so.employee_id
JOIN sale_item AS si
    ON si.sale_id = so.sale_id
JOIN product AS p
    ON p.product_id = si.product_id
WHERE so.status = 'COMPLETED';
```

## 6.3 每日销售统计视图

```
CREATE VIEW v_daily_sales AS
SELECT
    DATE(sale_time) AS sale_date,
    COUNT(*) AS order_count,
    SUM(total_amount) AS original_amount,
    SUM(discount_amount) AS discount_amount,
    SUM(payable_amount) AS sales_amount
FROM sale_order
WHERE status = 'COMPLETED'
GROUP BY DATE(sale_time);
```

# 7\. 订单总金额如何维护

采购单和销售单的 total_amount 都是明细金额之和。

采购总金额：

```
UPDATE purchase_order
SET total_amount = (
    SELECT COALESCE(SUM(line_amount), 0)
    FROM purchase_item
    WHERE purchase_item.purchase_id =
          purchase_order.purchase_id
)
WHERE purchase_id = 1;
```

销售总金额：

```
UPDATE sale_order
SET total_amount = (
    SELECT COALESCE(SUM(line_amount), 0)
    FROM sale_item
    WHERE sale_item.sale_id =
          sale_order.sale_id
)
WHERE sale_id = 1;
```

后面最好把这些操作写进存储过程。业务流程应该是：

```
创建草稿订单
    ↓
添加订单明细
    ↓
重新计算总金额
    ↓
确认订单
    ↓
修改库存
    ↓
写入库存流水
    ↓
修改订单状态
```

以上操作要放在同一个事务中。

# 8\. 删除规则建议

| **数据**               | **建议处理方式** |
| ---------------------- | ---------------- |
| 没有使用过的测试数据   | 可以删除         |
| 已产生订单的商品       | 停用，不删除     |
| 已产生采购记录的供应商 | 停用，不删除     |
| 已产生订单的员工       | 标记离职，不删除 |
| 已完成的销售单         | 不删除           |
| 已入库的采购单         | 不删除           |
| 库存流水               | 原则上永远不删除 |

因此大部分外键使用 ON DELETE RESTRICT，防止误删历史数据。

# 9\. 可选扩展：会员表

如果需要增加一点业务丰富度，可以添加会员表：

```
CREATE TABLE member (
    member_id BIGINT UNSIGNED AUTO_INCREMENT,
    member_no VARCHAR(30) NOT NULL,
    member_name VARCHAR(50) NULL,
    phone VARCHAR(30) NULL,
    points INT NOT NULL DEFAULT 0,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (member_id),
    UNIQUE KEY uk_member_no (member_no),
    UNIQUE KEY uk_member_phone (phone),
    CONSTRAINT chk_member_points
        CHECK (points >= 0),
    CONSTRAINT chk_member_status
        CHECK (status IN (0, 1))
) ENGINE = InnoDB;
```

再向 sale_order 添加会员外键：

```
ALTER TABLE sale_order
ADD COLUMN member_id BIGINT UNSIGNED NULL
    AFTER employee_id,
ADD KEY idx_sale_member (member_id),
ADD CONSTRAINT fk_sale_member
    FOREIGN KEY (member_id)
    REFERENCES member(member_id)
    ON UPDATE CASCADE
    ON DELETE RESTRICT;
```

不过会员功能不是核心，应该在采购、销售和库存流程完成后再做。
